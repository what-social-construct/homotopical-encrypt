# Homotopical Encryption

Homotopical Encryption is a research project on hidden-operator cryptography,
cellular-sheaf cochains, proof-carrying public artifacts, and a prospective
privacy-preserving ledger.

The repository contains:

- a Lean 4 formalization of the mathematical interfaces and proved
  relationships;
- Paper 1, covering the Harmonic Cochain Problem (HCP), its relationship to
  discrete CVP, and the full proximity projection;
- a Paper 2 workspace for protocol, runtime, consensus, and security-game
  concerns;
- Rust and Python prototypes whose eventual relationship to the Lean
  specifications remains an explicit trust-boundary problem.

The current priority is to make the Lean development and Paper 1 mutually
faithful. Rust and Python are research/protocol work, not the normative source
for the mathematics.

## Core Mathematical Idea

For a hidden sheaf or fibration representative $x$, restriction maps determine
the adjacent coboundaries and hence the degree-one Hodge--Laplacian:

$$
x
\longmapsto
\{R^x_{v\to e}\}
\longmapsto
(\delta_{0,x},\delta_{1,x})
\longmapsto
\Delta_{1,x}
\longmapsto
\bigl(\ker\Delta_{1,x},\pi_{H_x}\bigr).
$$

The degree-one cochain space has the Hodge splitting

$$
C_x^1
=
\ker(\Delta_{1,x})
\oplus
\operatorname{im}(\delta_{0,x})
\oplus
\operatorname{im}(\delta_{1,x}^{*}).
$$

In the encryption model, an observed cochain has the form $b=h+e$, where
$h$ is harmonic and $e$ lies in the exact/coexact complement. Recovery is
Hodge-theoretic: apply the harmonic projection determined by the hidden
operator.

“Homotopical” describes the surrounding security semantics. Public data
classifies a hidden representative only up to a lossy public class, while
different hidden representatives compatible with that class may induce
different operators and harmonic kernels.

The important contrast with ordinary known-lattice problems is therefore not
binary versus ternary matrix entries. It is a known operator versus a hidden
operator. Signed incidence entries and intuitionistic truth values occur in
the project, but neither is itself the source of HCP hardness.

## The Harmonic Cochain Problem

At the abstract level, HCP exposes a public class value $\alpha$ and a public
cochain-facing observation $b$. A hidden representative $x$ in the public
fiber $A_\alpha$ determines $\Delta_{1,x}$. The task is to recover the
harmonic component selected by that hidden operator without being given $x$
or $\Delta_{1,x}$.

This separates two problems:

1. identify or otherwise account for the operative hidden representative and
   its harmonic subspace;
2. solve the induced closest-vector problem once an explicit discrete lattice
   inside that subspace is supplied.

A real kernel $\ker(\Delta)$ is a vector subspace, not automatically a
discrete lattice. The Lean bridge therefore keeps the objects separate:

$$
\Lambda\subseteq W=\ker(\Delta),
$$

where $\Lambda$ is explicitly generated by integer coefficients and $W$ is
the real harmonic subspace. Orthogonal projection of a target onto $W$
preserves its closest vectors in $\Lambda$; it does not replace discrete CVP
with continuous projection.

## What Lean Establishes

The Lean workspace makes assumptions and conclusions explicit. Among its main
surfaces are:

| Surface | Machine-checked content |
|---|---|
| Hidden-operator ambiguity | **Hodge_Ambiguity**, **PublicCompatibleHodgeAmbiguity**, and **KernelAmbiguous** exhibit the failure of public data to select one harmonic kernel in the abstract model. |
| Known-lattice oracle limitation | **CVP_Oracle_Insufficient_For_Public_Hodge_Solving** rules out a uniformly correct public-only Hodge solver even when an exact oracle for explicitly presented lattices is granted. |
| Genuine discrete CVP | **CVP.lean** defines integer-generated lattices, closest lattice vectors, exact oracles, and an external efficiency/hardness schema. |
| HCP/CVP bridge | **HarmonicCVPBridge.solution_iff_projectedTarget** proves that projecting a target onto a harmonic subspace preserves the solutions of the supplied discrete CVP instance. |
| Public classes | **Axioms/HomotopyClass.lean** and **Axioms/HelferFOL.lean** define public classifiers, fibers, hidden class-membership witnesses, and non-faithful public collapse. |
| Infinite candidate geometry | **Ω_1_infinite** and the injective Grassmannian parameter family prove that the hidden harmonic-operator search space contains infinite families under the stated dimension hypotheses. |
| Spectral caution | **Spectrum_Not_Homotopy_Invariant** proves that equal harmonic dimension does not determine the full spectrum. It should not be read as a theorem about arbitrary homotopy-equivalent fibrations without an additional bridge. |
| Committed cochains | Sheaf-coherent acceptance identifies the committed mathematical object as an exact one-cochain $\operatorname{dec}_S(c)=\delta_0a$, from which Lean derives $\delta_1\operatorname{dec}_S(c)=0$. The opening $a$ is determined only modulo $\ker\delta_0$. |
| Proximity | The **Proximity** hierarchy carries frame/Plucker witness data through accepted cochain commitments, plane shadows, finite-field words, and the canonical Reed--Solomon/MCA endpoint, with near preservation and an explicit far-region non-collapse contract. |

CVP hardness itself remains an external complexity assumption. The Lean
development defines the problem and proves structural reductions and
separations; it does not prove that no efficient CVP algorithm exists.

## Privacy And Anonymity

The intended anonymity set for a public classifier value $\alpha$ is its
fiber

$$
A_\alpha=\pi^{-1}(\alpha).
$$

Lean currently formalizes the classifier/fiber semantics, hidden
class-membership witnesses, non-faithfulness, and infinite Grassmannian
candidate families. It does not yet prove that every protocol-relevant
$A_\alpha$ is infinite, nor does it define a uniform probability distribution
on an infinite class.

Accordingly, “$1/\infty=0$” is best read as shorthand for the intended
asymptotic anonymity interpretation: for a sequence of finite,
indistinguishable candidate sets whose cardinalities diverge, the baseline
uniform guessing probability tends to zero. A protocol theorem still needs to
connect the infinite candidate family to one public classifier fiber and state
the adversarial distribution/security game. Those concerns belong primarily
to Paper 2.

Likewise, quantitative work-factor targets such as $2^{256}$ require a
concrete parameter selection and reduction analysis. They are protocol/security
targets, not conclusions of Paper 1's current structural theorems.

## Cochain Commitments And Public Artifacts

A serialized cochain commitment records a modulus, declared edge count, residue
edge values, and topology hash. Its raw **WellFormed** predicate is deliberately
only a wire-shape condition.

Relative to a coherent sheaf datum $S$, mathematical acceptance is stronger:
the payload must be bound to $S$ and decode to an exact degree-one cochain.
Proof-carrying and runtime-facing artifact predicates inherit this semantic
refinement when an $S$-indexed context is available.

The exact $C^1$ value is the primary committed mathematical object. The raw
coboundary is not injective:

$$
\delta_0a=\delta_0a'
\quad\Longleftrightarrow\quad
a-a'\in\ker\delta_0.
$$

Consequently, authentication binds the exact payload bytes and their declared
context; unique binding of a degree-zero message would need a separate gauge or
reference anchor. At protocol level, the cochain, projected plane, and evidence
must bind the same canonical `SheafStateSnapshot` root. A short topology hash
alone is not a complete state snapshot.

The public artifact stack is:

~~~
hidden/private object
  -> compressed public shadow
  -> hash or commitment artifact
  -> proof-carrying artifact
  -> bounded runtime verification result
~~~

Hashes and proofs bind to mathematical objects; they do not replace them.

## Proximity Projection

The concrete one-way projection is:

~~~
private frame witness
  -> projective Plucker coordinate
  -> accepted cochain commitment
  -> plane shadow
  -> finite-field received word
  -> canonical Reed--Solomon/MCA target
~~~

The local syndrome and code-membership predicates are acceptance conditions on
the projected objects, not extra arrows in the chain. The near direction is
proved stage by stage. The far direction is a separate calibrated non-collapse
contract, as required for a gap reduction.

## System Direction

The broader repository separates four protocol jobs:

| Layer | Intended responsibility |
|---|---|
| State | `SheafState` is the outer state bus; immutable `SheafStateSnapshot` values bind sheaf-relevant context. |
| Proof | Certify that hidden objects induce valid public state transitions. |
| Ledger | Commit roots, nullifiers, cochain commitments, public shadows, and accepted proof artifacts. |
| Transport | Move private objects and proofs while addressing route and metadata privacy. |

Sheaf-aware transport is not itself the consensus validity layer. Proof
verification, state transition rules, ordering, fork choice, liveness, and
resource bounds remain distinct protocol obligations.

The categorical language in the design documents—transactions as morphisms,
state aggregation as a colimit, and $\Sigma/\Pi$ operations as an
encryption/decryption analogy—is architectural motivation unless a
corresponding Lean definition and theorem are cited. It should not be read as
already machine-checked protocol semantics.

## Proof Of Value And Consensus

Proof of Value (PoV) is the project’s proposed geometry-aware validity and
admissibility layer. The current direction combines:

- exact structural gates for cochain, Laplacian, and projection laws;
- three-valued oracle judgments for spectral boundary cases;
- Plucker/Grassmannian proximity evidence;
- proof-carrying cochain artifacts and canonical RS/MCA certificates;
- a separate authenticated weighted-quorum kernel for agreement work.

The $\sqrt 2$-style spectral window is presently an admissibility interface,
not a consequence derived solely from the geometry of the diagonal. Protocol
soundness, liveness, finality, sybil analysis, concrete security, and runtime
costs are Paper 2 concerns.

Lean now proves the arithmetic core of strict weighted quorum intersection and
binds votes to the relevant roots and round coordinates. Locking, round change,
validator admission, finality promotion, and liveness are still explicit open
protocol obligations; neither Heyting meet nor spectral convergence silently
supplies them.

See [CONSENSUS](docs/CONSENSUS.md),
[GATE_ARCHITECTURE](docs/GATE_ARCHITECTURE.md), and the
[Paper 2 workspace](papers/paper2/README.md).

## Three-Paper Program

1. [Paper 1](papers/paper1/README.md) is the core mathematics and
   formalization paper: HCP, hidden operators, the discrete-CVP comparison,
   cochain/public-artifact semantics, and the conditional source-to-RS
   projection bridge.
2. [Paper 2](papers/paper2/README.md) is the protocol and computer-science
   paper: proof-carrying verification, trust boundaries, consensus, security
   games, runtime behavior, and concrete costs.
3. [Paper 3](papers/proximity-prize/README.md) is the standalone coding paper,
   *Capacity-Radius Proximity for Smooth-Domain Reed--Solomon Codes*: universal
   list/MCA results, explicit coding instances, and radius analysis for the
   existing committed-cochain projection.

Paper 1 now also has an [actual integral cellular HCP family](lean/HCP/README.md):
its true operators and proved homological-test semantics instantiate the
shared-observation recovery obstruction and both CVP comparisons. The weighted
example distinguishes encoded integers in its declared lattice encoder.
Concrete visibility/storage, rotation and recipient key delivery remain
Paper 2 profile obligations.

Paper 3's universal coding results are independent of the HCP protocol.
Paper 1 retains the
application-specific projection bridge; the [shared manuscript parity register](SEMANTIC-PARITY.md)
records ownership, common notation, and definition issues across the split.
The [cochain-to-proximity trace](docs/COCHAIN_PROXIMITY_TRACE.md) follows the
same commitment payload through the actual projection and records the metric
comparison needed for the commitment-specific radius result.
The [storage and gate guide](lean/Protocol/Storage/README.md) records the same
snapshot/cochain context, incremental typed stages and local checkpoint
lifecycle. The nine generic coding statements have Lean endpoints; the
selected modular profile now has a proved three-level comparison and a capacity-far
payload. Stronger Euclidean/HCP comparisons retain their own scope.
Paper 2's [recommended first-submission scope](papers/paper2/SCOPE.md) centers
on one proof-carrying state transition; its [initial manuscript](papers/paper2/DRAFT.md)
records the shared validity and metric contracts. Product/whitepaper material is
unnumbered future work, outside these three manuscripts.

Detailed comparisons with other privacy, proof, consensus, and
post-quantum systems are working notes in
[COMPARISON](docs/COMPARISON.md). They are not part of the verified claim
surface and should be rechecked against current external systems before
publication.

## Trust Boundaries

| Component | Normative role |
|---|---|
| Lean | Mathematical objects, predicates, assumptions, and proofs. |
| Rust | Intended adversarial runtime boundary: parsing, canonical encoding, resource limits, proof verification, storage, networking, and consensus state transitions. |
| Python | Suspended legacy track. The former primitive and invariant layers are archived for provenance and future test-vector recovery; no current package/runtime checkpoint is claimed. |

The Lean-to-runtime correspondence is not verified extraction. Passing Lean
and Rust tests separately does not prove that the runtime implements the Lean
model. The remaining Python tree is intentionally non-runnable until its later
semantic-parity rewrite. See [TRUST_BOUNDARIES](docs/TRUST_BOUNDARIES.md).

## Verification

Build the principal Lean surfaces:

~~~sh
cd lean
lake build Sheaf Axioms TCB Chain Gates Proximity Protocol
~~~

Build Paper 1 with a full TeX installation:

~~~sh
cd papers/paper1
latexmk -pdf main.tex
~~~

The Rust prototype suite can be run independently:

~~~sh
cargo test --workspace
~~~

The Python suite is not a current verification target: its primitive and
invariant dependencies were retired to
[`docs/archive/python/`](docs/archive/python/README.md) pending a Lean-directed
runtime rewrite.

Avoid treating hard-coded test counts or component-completion percentages as
stable documentation. The CI configuration and current command results are the
source of truth for build status.
